## 二、最重要的发现：三级指纹

### 2.1 现在的设计长什么样

为了不每次都重新解析所有文件，系统用三级递进的方式判断「这个文件变了没有」：

```
第 1 级：看文件的大小和修改时间（极快，一次 stat）
          ↓ 变了才继续
第 2 级：算文件内容的指纹（较慢）
          ↓ 变了才继续
第 3 级：算每一段文字的指纹（最慢）
```

**打个比方**：像是图书馆查一本书有没有被换过——先看它在书架上的位置和厚度，一样就不翻开了。

**这个思路本身是对的**，能省掉绝大多数无用的重活。问题出在细节。

### 2.2 三个真实的漏洞

**漏洞一：换了另一本「一样厚」的书，光看外表发现不了**

第 1 级用「大小 + 修改时间」判断。只要有人：
- 在同一秒内改内容，且改完字节数还一样
- 或者用同步工具把修改时间「改回去」（`robocopy /COPY:T`、解压、git 检出、网盘同步都会这么干）

系统就会认为「没变」，**这次修改被永久漏掉**。

而且现在存的时间是浮点数秒。NTFS 的时间精度是 100 纳秒，浮点数在这个量级上的精度只有约 240 纳秒——**比文件系统还粗糙**，两次相差 100 纳秒的修改会被舍入成同一个数。

> **改法**：存纳秒整数；并加一条规则——**如果文件的修改时间比我们上次处理它的时间还早，就不信任外层判断**（文件比我们的记录还「旧」，说明时间戳被外部动过）。

**漏洞二：系统其实从来没看过文件本身**

第 2 级应该是「文件的指纹」，但实现里用的是**抽取出来的文字**的指纹。而真正的字节指纹函数 `hashing.hash_file()` 写了却**从来没被调用过**——是死代码。同一个文件的注释里还写着「sha256 of bytes」，文档、实现、意图三者对不上。

后果有三个：

- 只改了字体、图片、样式的 Word 文档，正文没变 → 报「未变化」，但你的预期是「更新了」
- 一份 `.docx` 和它的 `.md` 导出会被当成同一份资料
- 字节层面的任何变化都被彻底忽略

> **改法**：拆成两个意思不同的指纹，都存下来——
> - `file_hash`（文件字节）回答「文件变了没有」
> - `content_hash`（标准化文字）回答「能检索的内容变了没有」
>
> 这样系统能区分「文件变了但内容没变」（比如重新保存了一次 PPT）和「内容真的变了」。

**漏洞三：空白文件的指纹必然是同一个**

`hash_text("")` 对**所有**空文件都是同一个值 → 所有空文件会互相被判定为「重复」。现在恰好因为某个过滤条件躲过去了——**这是巧合，不是设计**。

> **改法**：内容为空的资料，指纹记为「无」，**永不参与查重**。

### 2.3 场景逐项核对

| 场景 | 现有设计会怎样 | 结论 |
|---|---|---|
| 文件改了，长度也变了 | 重新解析 | ✅ 正确 |
| 文件改了，**长度不变** | 可能误判「没变」 | ❌ 漏检 |
| 文件改了，修改时间在同一时刻内 | 可能误判「没变」 | ❌ 漏检 |
| 修改时间被外部工具改回去 | 可能误判「没变」 | ⚠️ 偶发漏检 |
| 文件**改名 / 移动** | 当成新资料，旧记录永久残留 | ❌ 你已点名的缺口 |
| 同名但不同目录 | 两个 ID；内容相同则走查重 | ✅ 合理 |
| 同名同路径被换成另一份 | 内容不同 → 判为更新 | ✅ 正确 |
| 真哈希碰撞（sha256） | 可忽略 | ✅ |
| **ID 被截断到 48 位**的碰撞 | 理论上 1670 万条才会撞；但没有检测 | ⚠️ 低 |
| Windows 路径大小写 | 会**覆盖**已存的原始路径写法 | ❌ 真 bug |
| **处理到一半崩溃** | 已入库的资料**重建时找不回来** | ❌ 最严重 |
| 写档案/缓存时崩溃 | 无半截文件 | ✅ 正确 |
| 日志写到一半 | 能自动跳过坏行 | ✅ 正确 |
| 解析器抛出非预期异常 | 失败**没有被记录** | ❌ 真 bug |

## 三、另一个严重问题：切片编号会漂移

切片（一段可检索的文字）现在的编号是 `(文档ID, 第几段, 文字指纹)`。

**问题**：在文档**开头**插入一段，后面每一段的「第几段」都变了 → 所有切片的编号全变，尽管文字一个字都没动。

- 对「重建索引」无害（同样的输入 → 同样的编号）
- 对**引用**有害：记忆卡片和生成的成果里存着 `doc:xxx#chunk=5`，文档一改，这个编号就**指向完全不同的文字**了

这直接伤到本项目最核心的诉求——**来源可追溯**。

> **改法**：把「内容身份」和「位置」分开。
> - 切片编号改为**内容寻址**：`(文档ID, 文字指纹, 该文字第几次出现)`
> - 同一段文字在文档里换了位置，编号不变
> - 「第几段」降级为纯排序字段
> - 定位符改成 `doc:<文档ID>#h=<文字指纹>`，人眼可读的位置另附

## 四、崩溃恢复：最严重的一条

导入每份资料时，系统做三件事：

1. 把资料写进**索引数据库**（每条提交一次）
2. 把资料写进**权威的来源清单** `sources.json`（**整批处理完才写一次**）
3. 追加一行日志

**如果用「重建索引」来恢复，它只会读来源清单。** 所以如果处理到一半崩溃：

```
索引数据库：有 12 份资料   ←── 已提交
来源清单：  只有 0 份      ←── 还没写

结果：这 12 份资料永远无法被重建找回
```

> **改法**：**权威层必须先于（或与）数据库提交同一处发生。** 即每处理一份：先登记来源清单并落盘，再提交数据库事务。
>
> 我还为这条写了一条专门的测试断言（测试计划场景 8b），它**在现有草稿上会失败**——先写测试，再改代码。

## 五、需要改的数据结构

| 对象 | 改动 | 为什么 |
|---|---|---|
| 版本号 | 1 → 2 | 索引是派生物，旧库直接丢弃重建，不迁移、无数据损失 |
| `doc` 表 | 新增 `mtime_ns`、`source_key`、`file_hash`、`norm_version`、`chunker_version`、`error`、`missing_at` | 精度、路径归一化、字节身份、版本指纹、失败留痕、缺失标记 |
| `doc` 表 | `content_hash` 允许为空 | 空内容不参与查重 |
| `doc` 表 | 唯一索引改到归一化后的路径上 | 修掉大小写覆盖 |
| **新表** `source_history` | 记录每条路径的首见/末见时间与原因 | 改名与移动的可追溯历史 |
| **新表** `doc_revision` | 记录每次内容变更 | 历史版本与变更记录 |
| `chunk` 表 | 编号改为内容寻址；新增 `chunk_hash`、`occurrence` | 引用不再漂移 |
| `meta` 表 | 新增「上次运行状态」 | 能识别上次没跑完 |
| 缓存布局 | `<文档ID>.txt` → `<文档ID>/<内容指纹>.txt`，保留最近 3 版 | 支持版本回退识别与「不读原文件」的重建 |
| 命令 | `add` / `index` / `index --rebuild [--from-source]` | 现有风格是单个小写动词（`init`、`doctor`），`rebuild-index` 的连字符风格不一致 |

### 重建要怎么改

设计成两档：

- **档 a（默认）**：从「档案 + 标准化文本」重建，**完全不读原始文件**。先写入一个临时数据库，全部成功后再原子替换——**旧索引全程可用**。这直接满足你说的「完成前不把不完整索引当作有效结果」。
- **档 b（`--from-source`）**：抽取器升级或缓存缺失时，才回到原始文件重新解析。

| **可以直接沿用** | 解析器契约与流水线分离；**用标准库解析 DOCX/PPTX（零第三方依赖）**；档案与缓存的原子写入；追加式日志 + 坏行容忍；FTS 双通道中文检索设计；原地重建（修掉过「删文件失败就静默复用旧库」的坑）；数据结构形状；幂等导入的整体思路 |

**使用方式：不复制、不执行、不 import。** 那 4 个缺陷都是结构性的（在提交顺序、失败路径、唯一索引、版本指纹上），逐行修补比重写风险更高。
