## 1. 三级指纹方案的审查（重点）

### 1.1 三个层级实际在回答什么

| 层 | 输入 | 回答的问题 | 性质 |
|---|---|---|---|
| L1 | `mtime` + `size` | 「**可能**变了没有」 | 概率性提示，**不是证明** |
| L2 | 抽取出的文本的 sha256 | 「可检索内容变了没有」 | 确定性，但看不见字节层变化 |
| L3 | 单个切片的 sha256 | 「这一片重写了没有」 | 确定性 |

**根本问题：现在这套方案把 L2 当成了「文件变了没有」的答案，而它回答的不是这个问题。**

`hashing.py` 的文档字符串写的是 "Level 2 (sha256 of bytes)"，但 `_p1_preview/brain/pipeline.py:215` 实际用的是 `hash_text(parsed.text)`；同时 `hash_file()`（字节级 sha256）**定义了却从未被调用**——是死代码。文档、实现、意图三者不一致。

### 1.2 场景逐项分析

| 场景 | 现在的行为 | 判断 | 处理 |
|---|---|---|---|
| 文件被修改，长度变了 | L1 未命中 → 重新解析 | ✅ 正确 | 保持 |
| 文件被修改，**长度不变** | 若 `mtime` 也恰好相同 → L1 误判「没变」 | ❌ 漏检 | 见缺陷 A |
| 文件被修改，`mtime` 落在同一时间粒度内 | 同上 | ❌ 漏检 | 见缺陷 A |
| 文件被修改，`mtime` 被外部回写（robocopy `/COPY:T`、解压、git checkout、同步盘） | 可能误判「没变」 | ⚠️ 偶发漏检 | 见缺陷 B |
| 文件**改名/移动** | 路径变 → 生成**新** `doc_id`，旧记录永久残留 | ❌ 用户已点名的缺口 | 见 §2 |
| 同名不同目录 | 路径不同 → 两个 `doc_id`；内容相同 → 走查重 | ✅ 合理 | 补 `source_history` |
| 同名同路径被换成另一份文件 | 内容哈希不同 → 判定为更新 | ✅ 正确 | 保持 |
| sha256 碰撞 | 可忽略 | ✅ | 文档化 |
| **id 截断到 48 bit** 的碰撞 | `short_hash` 取 sha1 前 12 位；生日界 ≈ 2²⁴ ≈ 1670 万条 | ⚠️ 个人语料安全，但无检测 | 见缺陷 I |
| Windows 路径大小写 | `doc_id` 归一化后相同，但唯一索引建在**原始串**上 | ❌ 会覆盖 `source_ref` | 见缺陷 J |
| 批处理中途崩溃 | DB 逐条提交，`sources.json` 只在批尾保存 | ❌ **已入库资料无法被 rebuild 找回** | 见缺陷 K |
| 写档案/缓存中途崩溃 | `tmp` + `os.replace`，无半截文件 | ✅ 正确 | 可能留孤儿档案 → 加检查 |
| journal 写到一半 | `tail()`/`counts()` 跳过坏行 | ✅ 正确 | 保持 |
| 非 `ParseError` 的解析器异常 | 对**不存在**的 doc 行执行 `UPDATE` → 0 行受影响 | ❌ 失败未被记录 | 见缺陷 L |

### 1.3 缺陷清单

**A. mtime 精度不足（真 bug）**
`doc.mtime` 是 `REAL`（float64 秒）。NTFS 的时间戳是 100 ns 粒度；float64 在 ~1.7×10⁹ 附近的 ULP 约 240 ns，**两次相差 100 ns 的修改会被舍入成同一个数**。exFAT/FAT32/SMB 共享更粗（1–2 秒），「同一秒内改内容且长度不变」必然漏检。
→ 改：存 `st_mtime_ns`（INTEGER，精确）。并增加**不可信窗口**：若 `mtime` 落在 `now - grace`（默认 2 s）内，或 `mtime` 早于该记录的 `imported_at`，一律不信任 L1，强制进入 L2。

**B. mtime 可被外部回写**
→ 改：L1 只作为优化，绝不作为正确性依据。上面的「`mtime < imported_at` 不可信」是一条便宜且强的信号——文件比我们上次处理它还「旧」，说明时间戳被外部改过。另外提供 `add --verify` 做全量重算。

**C. 字节层信息丢失（设计缺陷）**
只改字体/嵌图/样式而正文不变的 DOCX 会报「未变化」，用户预期是「更新」。同时 `.docx` 与它的 `.md` 导出会被当成同一份资料。
→ 改：**拆成两个语义不同的哈希，都存**：

| 字段 | 输入 | 回答 |
|---|---|---|
| `file_hash` | 原始字节 sha256 | 文件变了没有 |
| `content_hash` | 标准化文本 sha256（含归一化版本号） | 可用于检索的内容变了没有 |

状态机据此区分 `unchanged` / `metadata_only`（文件变了、内容没变）/ `updated`。

**D. 空内容的哈希碰撞是必然的（巧合性正确）**
`hash_text("")` 对所有空文件是同一个值 → 所有空文件互为「重复」。预览里恰好因为 `doc_hash=''` 被查重的 `doc_hash <> ''` 条件过滤掉才没爆——**这是巧合，不是设计**。
→ 改：内容为空的资料 `content_hash = NULL`，**永不参与查重**。

**E. 哈希输入没有版本号**
归一化规则（去 frontmatter、统一换行、去零宽字符……）一旦调整，旧 `content_hash` 与新规则不可比，但系统不知道。
→ 改：`content_hash = sha256(norm_version ‖ "\x00" ‖ normalized_text)`，并把 `norm_version` 入库。

**F. `ordinal` 污染了切片的「内容身份」（最重要的设计缺陷）**
`chunk_id = sha1(doc_id, ordinal, chunk_text_hash)[:12]`。在文档**开头**插入一段，后面所有切片的 id 全变，尽管文字一个字没动。
- 对 `--rebuild` 无害（同一输入 → 同一 id）。
- 对**引用**有害：记忆卡片和生成成果里存的 `doc:<id>#chunk=5`，在文档被编辑后会指向完全不同的文字。这正是本项目最核心的「来源可追溯」诉求。

→ 改：把「内容身份」与「位置」分开
- `chunk_id = sha1(doc_id, chunk_hash, occurrence)` —— **内容寻址**；同一段文字在文档里换了位置，id 不变
- `occurrence` = 同一文档内相同文本的第几次出现（解决重复段落）
- `ordinal` 降级为纯排序字段，不参与身份
- 定位符改为 `doc:<doc_id>#h=<chunk_hash[:10]>`，可读位置另附 `#ordinal`

**G. 切片参数变化不触发重建（真 bug）**
改了 `chunk.target_chars` 再跑 `add`，L1/L2 命中 → 返回 `skipped` → **索引里的切片还是旧的**。
→ 改：入库 `chunker_version`（= 切片算法版本 + `target_chars` + `max_chars` 的指纹）；与当前值不一致时绕过 L1/L2。

**H. 抽取器升级不触发重建（真 bug）**
schema 里有 `extractor_version` 列，代码**从不写入、从不比较**。
→ 改：写入并比较；不一致时绕过 L1/L2。

**I. id 截断无碰撞检测**
48 bit 对个人语料是安全的，但没有检测机制，出问题时是静默的错误合并。
→ 改：插入时若发现同 id 但 `content_hash` 不同 → 报错并停止，`doctor` 增加同 id 异内容的一致性检查。

**J. Windows 路径大小写（真 bug）**
`ids.doc_id()` 对 `C:\A.md` 与 `c:\a.md` 归一化后得到**同一个 id**，但 `UNIQUE(source_kind, source_ref)` 建在**原始串**上 → 第二次 UPSERT 命中主键冲突，把 `source_ref` 覆盖成后看到的那个写法。
→ 改：新增 `source_key`（归一化）列，唯一索引改建在 `(source_kind, source_key)` 上。

**K. 提交顺序让「已入库」与「可重建」不一致（最严重的真 bug）**
`ingest_file` 每条 commit 一次 DB，但 `registry.save()` 在**整批结束后**才执行。批中崩溃 ⇒ DB 里有 doc，`sources.json` 里没有 ⇒ **这些资料永远无法被 rebuild 找回**，而 rebuild 是唯一的索引恢复路径。
→ 改：**权威层的写入必须先于或与 DB 提交同一处发生**。即每条资料：先 `registry.add` + 落盘，再提交该条的 DB 事务。

**L. 非 `ParseError` 异常下的失败未被记录（真 bug）**
`pipeline.py:209` 在未先 `upsert_doc` 的情况下调用 `set_status`，而 `set_status` 是 `UPDATE ... WHERE doc_id=?`——首次处理就抛非预期异常时匹配 0 行，失败只写进了 `meta`，`doc` 表里没有这条记录。
→ 改：任何失败路径都先 upsert 一条 `status='failed'` 的记录，再写 `error`。

**M. 重建会删除 missing 来源（与需求冲突）**
`reindex_all` 对找不到的文件执行 `registry.remove()`。但用户明确要求「改名或移动后不得仅凭路径假设它是新资料」——删掉记录等于**销毁了移动识别所需的唯一线索**。
→ 改：改为 `mark_missing()`（记 `missing_at`），保留记录；只有显式 `--prune` 才真删。

**N. 重建强制重新解析全部原始文件（与需求冲突）**
`reindex_all` 对每条来源调用 `ingest_file(..., force=True)`。而用户要求「以可信的档案与标准化文本为基础」「不重新处理所有原始文件，除非必要」。同时 `_write_doc_artifact` 写出的档案**缺少 `file_hash`、版本字段、status**，不足以支撑不读原文件的重建。
→ 改：见 §4 的两档重建。

**O. `apply_dedup` 无条件重写**
每次批量结束都对所有重复项执行 DELETE + UPDATE，即使状态没变。功能上幂等，但写放大明显。
→ 改：只在结果确实变化时写。

**P. canonical 被重置为 PENDING 后当次不重索引**
`apply_dedup` 把 canonical 从 `DUPLICATE` 改回 `PENDING` 后，本次运行不会再处理它 → 可能留下「已登记但没有任何切片」的资料，直到下次运行。
→ 改：本次运行内重新索引 PENDING 的资料。

**Q. `state` 的 `updated_at` 每次都变（幂等性瑕疵）**
`SourceRegistry.save()` 与 `add()` 每次都写 `now_iso()`。语义上幂等，但**文件内容每次都不同**——`data/` 是打算可提交、可 diff 的。
→ 改：仅在字段真正变化时更新 `updated_at`。

**R. FTS 查询错误被伪装成「没找到」**
`Store._fts_search` 用 `except sqlite3.OperationalError: return []` 吞掉查询异常。查询语法写错时，用户看到的是「没有相关内容」，而真实原因是 bug。
→ 改：区分「无匹配」与「查询执行失败」，后者必须抛出。

**S. 超长单句无硬性上限**
`chunk._explode` 只在 `len(para) > MAX_CHARS` 时退化为按句切；**单句本身超长时不再切**。一个 100 KB 的无标点单行文件会产出**一个巨大切片**，直接撑爆上下文预算。
→ 改：加硬性上限，超限强制按字符窗口切分。

**T. 默认值有两个真源**
`init.py` 的 `DEFAULT_CONFIG` 与 `config.py` 的默认值重复定义，改一处忘另一处就会分叉。
→ 改：`init` 改为调用 `config.default_config().to_json()`。

### 1.4 结论

三级结构本身**是对的**（省 IO 的思路正确），但需要五处实质性修改：

1. **L1 降级为「提示」**，并加 `mtime_ns` 精度 + 「不可信窗口」规则（缺陷 A、B）
2. **L2 拆成 `file_hash` 与 `content_hash` 两个语义不同的哈希**，且内容哈希带版本号（缺陷 C、E）
3. **L3 改为内容寻址**，把 `ordinal` 从身份里拿出来（缺陷 F）
4. **增加参数版本指纹**（切片参数、抽取器、归一化规则），任一变化即绕过 L1/L2（缺陷 G、H、E）
5. **修正提交顺序与失败记录**，保证「已入库 ⇒ 可重建」，且失败必留痕（缺陷 K、L）

## 2. 查重与更新规则（重新定义）

### 2.1 三层身份

| 层 | 键 | 回答 |
|---|---|---|
| 来源身份 | `(source_kind, source_key)` → `doc_id` | 这是不是同一条来源？ |
| 字节身份 | `file_hash` | 文件被改过没有？ |
| 内容身份 | `content_hash` | 可检索的内容变了没有？ |

### 2.2 导入一个路径时的判定顺序

```
1. 按 (kind, source_key) 查 → 命中 = 同一来源
      file_hash 相同                       → unchanged      （连 stat 都不需要）
      file_hash 变、content_hash 相同       → metadata_only  （文件变了，可检索内容没变）
      content_hash 变                       → updated        （替换该 doc 的全部切片）
      版本指纹不匹配（切片/抽取/归一化）      → reindexed     （强制重算）

2. 未命中 → 按 file_hash 查 status='missing' 且有历史路径的记录
      恰好 1 条   → moved       保留 doc_id，追加 source_history，更新 source_ref
      多条        → moved(歧义) 取 last_seen_at 最早、再按 source_ref 字典序最小的一条，
                                并在 source_history 写明歧义与选择依据
      0 条        → 进入 3

3. 未命中 → 按 content_hash 查现有 indexed 记录
      命中且 file_hash 不同 → duplicate（建档案，指向 canonical）
      未命中                → new
```

### 2.3 历史版本保留策略（明确）

- `source_history` 表：每条路径的 `first_seen_at` / `last_seen_at` / `reason`（`new`/`moved`/`renamed`/`reappeared`）。
- **只有当前版本**的切片进 `chunk`；历史切片不留（体积）。
- 档案 JSON 追加 `revisions[]`：`{at, file_hash, content_hash, char_count, chunk_count}`。
- 正文历史保留在 `cache/<doc_id>/<content_hash>.txt`，**保留最近 3 版**（可配）。
  - 好处一：「内容被改回旧版」可被识别（命中原有 hash）
  - 好处二：重建的档 a 有第二来源
  - 代价：cache 从 `<doc_id>.txt` 变为 `<doc_id>/<content_hash>.txt`
- 原始文件**永不修改**——这条在所有路径上都是硬约束。

### 2.4 幂等性与中断

- 同一命令重复运行：`doc` / `chunk` / `chunk_fts` / `chunk_fts_cjk` 行数不变，`sources.json` 内容也不变。
- 每条资料一个事务；**先登记权威层，再提交派生层**。
- `meta` 增加 `last_run_state`（`running`/`complete`/`failed`），启动时若发现上次是 `running` → `doctor` 报警，`add` 先做一次对账。
- 孤儿档案（有 `data/docs/*.json` 但无 DB 行）由 `doctor` 报出，`rebuild` 忽略。

## 3. Schema 与接口修改清单

### 3.1 `SCHEMA_VERSION: 1 → 2`

索引是派生物，因此**不做数据迁移**：检测到版本不符即丢弃重建（现有行为已如此）。

### 3.2 `doc` 表

| 变更 | 字段 | 说明 |
|---|---|---|
| 新增 | `mtime_ns INTEGER` | 精确时间戳；`mtime REAL` 保留供阅读 |
| 新增 | `source_key TEXT NOT NULL` | 归一化路径；唯一索引改建在 `(source_kind, source_key)` |
| 新增 | `file_hash TEXT` | 原始字节 sha256 |
| 修改 | `content_hash` | 允许 **NULL**（空内容不参与查重） |
| 新增 | `norm_version TEXT NOT NULL` | 文本归一化规则版本 |
| 新增 | `chunker_version TEXT NOT NULL` | 切片算法 + 参数指纹 |
| 补用 | `extractor_version TEXT` | 列已存在，**必须写入并比较** |
| 新增 | `error TEXT` / `error_at TEXT` | 替代 `meta` 里的 `error:<doc_id>` hack |
| 新增 | `missing_at TEXT` | 缺失标记，替代直接删记录 |

### 3.3 新表

```sql
CREATE TABLE source_history (
  doc_id        TEXT NOT NULL,
  source_kind   TEXT NOT NULL,
  source_ref    TEXT NOT NULL,
  source_key    TEXT NOT NULL,
  reason        TEXT NOT NULL,      -- new | moved | renamed | reappeared
  first_seen_at TEXT NOT NULL,
  last_seen_at  TEXT NOT NULL,
  note          TEXT,
  PRIMARY KEY (doc_id, source_key)
);

CREATE TABLE doc_revision (
  doc_id       TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  file_hash    TEXT,
  char_count   INTEGER,
  chunk_count  INTEGER,
  recorded_at  TEXT NOT NULL,
  PRIMARY KEY (doc_id, content_hash)
);
```

### 3.4 `chunk` 表

| 变更 | 字段 | 说明 |
|---|---|---|
| 新增 | `chunk_hash TEXT NOT NULL` | 切片归一化文本的 sha256（独立于 id，便于校验） |
| 新增 | `occurrence INTEGER NOT NULL DEFAULT 0` | 同文档内相同文本的第几次出现 |
| 语义变更 | `chunk_id` | 由 `(doc_id, ordinal, hash)` 改为 `(doc_id, chunk_hash, occurrence)` |
| 语义变更 | `ordinal` | 降级为纯排序字段 |

### 3.5 `meta` 表

新增键：`last_run_state`、`last_run_at`、`last_run_mode`。

### 3.6 接口清单

| 接口 | 现状 | 改为 |
|---|---|---|
| `hashing.fingerprint()` | `mtime: float` | 返回 `mtime_ns: int` + `size`；新增 `trust_level(record)` 判定「是否可信」 |
| `hashing.hash_file()` | 死代码 | pipeline **必须调用** |
| `hashing.hash_text()` | 无版本 | `hash_normalized(text, norm_version)` |
| `ids.doc_id()` | 用原始 ref | 用 `source_key` |
| `ids.chunk_id()` | 含 `ordinal` | `(doc_id, chunk_hash, occurrence)` |
| `source.locator_chunk()` | `#chunk=<ordinal>` | `#h=<chunk_hash[:10]>` |
| `state.SourceRegistry.add()` | 每次改 `updated_at` | 仅字段真变化时才改 |
| `state.SourceRegistry.remove()` | 直接删 | 改为 `mark_missing()`；`--prune` 才真删 |
| `state.SourceRegistry` | 批尾统一 save | 支持**单条立即落盘** |
| `store.upsert_doc()` | 旧字段集 | 增加 `file_hash/mtime_ns/source_key/norm_version/chunker_version/error/missing_at` |
| `store.set_status()` | 借 `meta` 存错误 | 写 `doc.error` |
| `store.integrity()` | 3 项检查 | 增加：孤儿档案、空 `content_hash` 却参与查重、同 id 异内容、`missing_at` 与磁盘不一致、版本字段缺失 |
| `store._fts_search()` | 吞掉 `OperationalError` | 区分「无匹配」与「查询失败」 |
| `pipeline.ingest_file()` | 先 DB 后 registry | **先 registry 落盘，再提交 DB** |
| `pipeline.apply_dedup()` | 无条件重写 | 仅在结果变化时写 |
| `pipeline.reindex_all()` | 强制重解析原文件 | 两档重建（§4） |
| `chunk.chunk_segments()` | 超长单句不切 | 加硬性字符上限 |
| `cli/init.py::DEFAULT_CONFIG` | 与 `config.py` 重复 | 改为调用 `config.default_config().to_json()` |

## 4. 可重建的索引

### 4.1 命令

```
recall.py index --rebuild                 # 档 a：从归档重建（默认，不读原始文件）
recall.py index --rebuild --from-source   # 档 b：从原始文件重新解析
```

### 4.2 档 a —— 从归档重建（默认）

满足「以可信档案与标准化文本为基础」「不重新处理所有原始文件」。

1. 建新库到**临时路径** `index/.rebuild-<pid>.db`
2. 遍历 `data/docs/*.json`（权威档案）
3. 从 `cache/<doc_id>/<content_hash>.txt` 读标准化文本
4. 用当前切片参数重新切片（切片是纯函数，确定）
5. 写 doc / chunk / 两个 FTS
6. 全部成功 → `VACUUM` → `os.replace()` **原子替换** `index/recall.db`
7. 任一步失败 → 保留旧库不动，删临时库，报明确错误与失败清单

**关键保证：旧的 `recall.db` 在整个过程中保持可用。** 只有全部成功才原子替换——这直接满足「重建完成前，避免把不完整索引当作有效结果」。

某条档案的 cache 文本缺失 → 该条**自动降级**到档 b（读原始文件）；原始文件也不在 → 标 `missing` 并**明确列出**，不静默跳过。

### 4.3 档 b —— 从原始文件重建

抽取器版本变化、或 cache 丢失时使用。逐条重新解析原始文件（只读），流程同档 a。

### 4.4 验收

- 重建前后，对固定查询的 `chunk_id` 集合**逐字节相等**（除因切片参数变化而**有意**变化时，此时 `chunker_version` 也已变，需在报告里显式说明）。
- 重建期间旧库可用：重建中途 kill 进程 → 旧库仍能查询，且 `last_run_state` 为 `running`。
- `data/`、`cache/`、原始文件在重建全程**零写入**（用文件指纹前后比对验证）。

## 5. `_p1_preview/` 审查意见

**总评：主干可留，但不要整体复制。** 有 4 个必须先修的正确性缺陷，另有若干「巧合性正确」。

### 5.1 必须修（正确性，P1-P0 级）

| # | 位置 | 问题 |
|---|---|---|
| 1 | `pipeline.ingest_paths` / `reindex_all` | `registry.save()` 在批尾，DB 逐条提交 → 批中崩溃的资料无法被 rebuild 找回（缺陷 K） |
| 2 | `pipeline.ingest_file` 的 `except Exception` 分支 | 未先 upsert 就 `set_status` → 首次失败未记录（缺陷 L） |
| 3 | `ids.doc_id` + `schema` 的 `ux_doc_src` | 归一化后同 id、唯一索引在原始串上 → `source_ref` 被覆盖（缺陷 J） |
| 4 | 版本指纹缺失 | 改切片参数或升级抽取器后，索引静默过期（缺陷 G、H） |

### 5.2 应当改（设计）

5. `file_hash` 从不使用；`hashing.py` 文档与实现不符
6. `chunk_id` 含 `ordinal` → 引用会漂移
7. 空内容哈希必然碰撞，靠 `<> ''` 过滤是巧合
8. `reindex_all` 删除 missing 来源 → 丢失移动识别线索
9. `reindex_all` 强制重解析原文件 → 违反需求
10. `_write_doc_artifact` 缺 `file_hash` / 版本字段 / status → 不足以支撑档 a
11. `apply_dedup` 无条件重写 → 写放大
12. canonical 重置为 PENDING 后当次不重索引 → 可能留下无切片的资料
13. `state` 每次改 `updated_at` → 文件内容非幂等
14. `_fts_search` 吞掉 `OperationalError` → 把查询 bug 伪装成「没找到」
15. `chunk` 对超长单句无硬上限
16. `init.py` 的 `DEFAULT_CONFIG` 与 `config.py` 重复定义

### 5.3 可以直接沿用（已实测有效）

- `ParseError` 契约；解析器与流水线彻底分离
- `zipfile` + `ElementTree` 解析 DOCX/PPTX（**零第三方依赖**）
- 档案与缓存的原子写（`tmp` + `os.replace`）
- `imports.jsonl` 追加式日志 + 脏行容忍
- FTS 双通道（trigram + 逐字）设计与 CJK 分词
- `store.reset()` 原地重建（修掉了「删文件失败则静默复用旧库」）
- 幂等导入的整体思路（草稿实测 13 项通过）
- `ParsedDoc` / `Segment` / `Chunk` 的数据形状

### 5.4 使用方式

**不复制、不执行、不 import。** 仅作为设计参考；P1 的代码按 §6 顺序**重新编写**，把 5.1 的 4 项在源头解决。

## 6. CLI 命名

**现有风格**：全部是单个小写英文动词，无连字符、无多词 —— `init`、`doctor`。`rebuild-index` 是 kebab-case，与现有风格不一致。

**决定**：

| 命令 | 作用 |
|---|---|
| `recall.py add <path...>` | 导入 |
| `recall.py index` | 查看索引状态 |
| `recall.py index --rebuild` | 重建（档 a） |
| `recall.py index --rebuild --from-source` | 重建（档 b） |
| `recall.py search` | P2 才实现，本轮不注册 |

理由：动词数量少，`index` 与 `index/` 目录语义一致，`--rebuild` 是修饰而非新动词。
**备选**：`reindex` 作为独立动词（更明确，但多一个词）。如你偏好，一句话即可改。
