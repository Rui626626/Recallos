# P1 测试计划

> 状态：**计划，未实现。** 本文件定义 P1 的验收标准；代码按 [`05-P1设计审查.md`](05-P1设计审查.md) §7 的顺序编写。
> 运行方式（P1 完成后）：`python tests\test_p1.py`，并必须同时通过 `python tests\test_p0.py`。

---

## 0. 测试原则

1. **只断言可观测事实**：磁盘上的文件、数据库里的行、退出码、stdout 的 JSON 结构。
2. **不断言日志文字**。日志里出现「成功」不算通过。
3. **全部黑盒**：通过 `subprocess` 驱动真实 CLI，`RECALLOS_ROOT` 指向临时根。
4. **绝不动用户的真实文件**：所有 fixture 都在临时目录里现造。
5. **每个断言都要能失败**：写完测试后，故意把被测行为改坏一次，确认测试变红。

## 2. 场景与断言

### 场景 1 — 五种格式的正常导入

**动作**：`add <fixture_dir>`

**断言**
- `doc` 表中 `extractor` 的集合包含 `markdown`、`text`、`docx`、`pptx`、`pdf:pypdf`
- 每种格式至少 1 条 `status='indexed'` 且 `chunk_count > 0`
- `data/docs/` 下 JSON 文件数 == `doc` 表行数
- `cache/<doc_id>/<content_hash>.txt` 对每条 `indexed` 资料都存在且**非空**
- `chunk` 表行数 == 两条 FTS 表的行数
- `store.integrity()` 返回 `{}`
- 退出码 `0`

**反向验证**：把 DOCX 解析器的返回值改成空列表 → 本场景必须变红。

---

### 场景 2 — 重复导入不产生重复档案

**动作**：`add <dir>` 两次

**断言**
- 第二次运行后，`doc` / `chunk` / `chunk_fts` / `chunk_fts_cjk` 四个行数**与第一次完全相同**
- 第二次 `by_status` 全部是 `skipped`，`chunks_added == 0`
- `sources.json` 的**文件内容**逐字节相同（含 `updated_at` 不变 —— 对应缺陷 Q）
- `lecture01.md` 与 `dup-copy.md`：恰好一个 `indexed`、一个 `duplicate`；`duplicate.chunk_count == 0` 且 `duplicate.duplicate_of == canonical.doc_id`；两者 `doc_hash` 相同
- 退出码 `0`

---

### 场景 3 — 同一路径内容更新

**动作**：改 `lecture02.md`（追加一段）→ `os.utime` 保证 mtime 可见变化 → `add` 两次

**断言**
- 只有 `lecture02.md` 的 `content_hash` 与 `file_hash` 变化，其余资料的 `content_hash` 一个都不变
- `imported_at` **不变**，`updated_at` 变
- 旧切片已被替换：`chunk` 中该 doc 的行数等于新内容的切片数，且**不存在**任何旧 slice 的 `chunk_hash`
- `doc_revision` 表新增一行，`cache/<doc_id>/` 下新增一个版本文件
- 后续再跑一次 `add` → 该 doc 变 `skipped`（幂等）
- 退出码 `0`

**附：仅字节变化、内容不变**
- 用 python-pptx 重新保存 `deck.pptx`（时间戳元数据变化、正文不变）
- 断言：`file_hash` 变、`content_hash` **不变**、状态为 `metadata_only`、`chunk` 行数不变

---

### 场景 4 — 文件改名 / 移动后的识别

**动作**
1. `add` 建立基线，记下 `lecture01.md` 的 `doc_id`
2. `os.rename` 把 `lecture01.md` 移到另一个目录 → `add`
3. 单独验证「同名不同目录」：把 `notes.txt` 复制到另一个目录 → `add`

**断言**
- 移动：**`doc_id` 不变**；`status='indexed'`；`source_ref` 更新为新路径；`source_history` 新增一条 `reason='moved'`；`chunk_id` 集合不变（内容没变）
- 旧路径不再是任何 doc 的当前 `source_ref`
- 移动后**不产生**新的 `doc` 行（行数不变）
- 复制：产生**新的** `doc_id`，且与源文件 `content_hash` 相同 → 按查重规则标 `duplicate`
- 歧义场景：同时把两份缺失记录造得与同一内容匹配 → 断言按 `(last_seen_at 最早, source_ref 字典序)` 选定，且 `source_history.note` 写明了歧义

### 场景 5 — 中文标点、空格、短词与常见查询

在场景 1 的库上直接查（本场景只读，不改库）。

| 查询 | 期望 |
|---|---|
| `复习资料` | 命中，snippet 用 `«»` 高亮，出处在 markdown 资料 |
| `复习` | 命中（走逐字通道） |
| `机器学习三要素` | 命中 |
| `数据、模型、算法` | 含中文顿号，不报错；命中或明确无命中均可，但**退出码必须 0** |
| `反向 传播` | 含空格，不报错，退出码 0 |
| `"""` | 纯标点，返回空，退出码 0 |
| `A` | 单字符，返回空或少量命中，退出码 0，不崩 |
| `zzz不存在的词组qqq` | 返回空，`candidates == 0`，退出码 0 |

**附加断言**
- 任何查询的 `token_estimate <= budget`
- 同 doc 的条目 `<= max_chunks_per_doc`
- snippet 中不出现内部标记控制字符（`\x01` / `\x02`）
- 故意把 FTS 表名写错 → 断言**抛出**而不是返回空（对应缺陷 R）

---

### 场景 6 — 空文件、损坏文件、不支持的格式

**动作**：`add <dir>`

**断言**
- 退出码：**非 0**（因为存在 `failed`），且 stderr 有可读消息、**无 traceback**
- `empty.md`：`status='failed'`，`error` 非空且提到「空」，且 `content_hash IS NULL`（不参与查重）
- `broken.docx`：`status='failed'`，`error` 提到无法解析
- `unsupported.xyz`：**根本不进入扫描**（不在白名单），`doc` 表中不存在该路径
- `scanned.pdf`：`status='failed'`，`error` 含 `OCR` 提示
- 其余文件全部 `indexed`，不受连带影响
- `imports.jsonl` 中能按 `path` 找到上述每条失败记录，且 `error` 字段非空
- `doctor` 不因存在 `failed` 而失败（失败是正常状态）

### 场景 7 — 导入失败后再次执行

**动作**
1. `add`（含损坏文件）
2. 修好 `broken.docx`（重新写一个合法文件）→ `add`
3. 再 `add`（不改任何东西）

**断言**
- 步骤 2：`broken.docx` 从 `failed` 变为 `indexed`，`error` 被清空，`chunk_count > 0`
- 步骤 2：其余文件不受影响
- 步骤 3：全部 `skipped`，四个行数与步骤 2 完全相同
- 全程退出码：步骤 1 非 0，步骤 2、3 为 0

---

### 场景 8 — 事务中断与索引写入失败

**8a 索引写入失败（真实 OS 级故障）**
- 测试进程用另一个连接对 `index/recall.db` 执行 `BEGIN EXCLUSIVE`，把库锁住
- 运行 `add`
- 断言：退出码非 0；`doc` 表**没有**出现半成品记录（要么没有该 doc，要么状态是 `failed` 且 `error` 含 `locked`）；`data/docs/` 下没有对应孤儿档案；解锁后再 `add` → 全部成功且行数正确

**8b 批处理中途被杀（真的杀进程）**
- 用 `Popen` 启动 `add`，读到进度输出若干条后 `terminate()`
- 断言：
  - `index/recall.db` 仍能打开，`integrity()` 为 `{}`
  - **`sources.json` 里登记的资料集合 ⊇ `doc` 表中已提交的资料集合**（对应缺陷 K —— 这条断言在现有草稿上**会失败**）
  - `meta.last_run_state == 'running'`（能识别上次没跑完）
  - 重新 `add` → 收敛到完整集合，且无重复 `doc_id`、无重复 `chunk_id`
- 同样在 `index --rebuild` 中途杀掉：旧库必须仍然可查询

**8c 写档案时崩溃**
- 人为在 `data/docs/` 放一个孤儿 JSON（内容合法但 DB 里无对应 doc）
- 断言：`doctor` 报出孤儿；`index --rebuild` **忽略**它且不报错

---

### 场景 9 — 重建索引后数据仍然完整

**动作**
1. 记下 `chunk` 全部 `chunk_id` 的排序集合、每条 doc 的 `content_hash`
2. `index --rebuild`（档 a）
3. 比较

**断言**
- `chunk_id` 集合**逐字节相等**
- 每条 doc 的 `content_hash` / `file_hash` / `title` / `source_ref` 不变
- 两条 FTS 的行数与 `chunk` 行数一致，`integrity()` 为 `{}`
- 固定查询的命中 locator 集合与重建前相同
- **重建期间没有读任何原始文件**：用文件访问时间或（更可靠地）把原始文件目录整体改名后再重建 → 仍能成功（档 a 只读 `data/` 与 `cache/`）
- `index --rebuild --from-source` 得到同样的 `chunk_id` 集合
- 退出码 `0`

### 场景 10 — 原始文件未被修改

**在整个测试套件开始前与结束后各采集一次**

对 fixture 目录做全量快照：`(相对路径, size, mtime_ns, sha256(bytes))`，并按路径排序。

**断言**
- 两次快照**完全相等**
- fixture 目录内的文件数量不变（没有新增、没有删除）
- 特别地：`add`、改名场景、`index --rebuild` 之后都没有改动原始文件

这条覆盖了用户的硬约束「不允许擅自修改、移动、重命名或删除原始文件」。

## 4. 关于故障注入的说明

场景 8 的三种做法**都不需要**在生产代码里留测试开关：

- 8a 用 SQLite 自己的排他锁制造真实写失败
- 8b 真的 `terminate()` 进程
- 8c 手工放一个孤儿文件

这样测试不依赖任何「只在测试时存在」的分支，也就不会出现「测试通过但生产路径没被测到」的情况。

**如果你希望有确定性的准点中断**（比如「正好在处理到第 3 条时崩溃」），那需要在流水线里加一个由环境变量 `RECALLOS_FAULT` 控制的中断点。这会往生产代码里引入一个测试专用分支，**我不建议**；如你需要，请明确告知。
